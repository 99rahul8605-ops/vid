# Advanced Video Unlock + Referral Bot

## Core user flow

1. User `/start`
2. Required groups/channels are shown with Join buttons.
3. By default, admin-added required chats use **approval / join-request links** generated by the bot.
4. When Telegram sends a `chat_join_request` update, the bot stores that recent pending request in MongoDB.
5. User taps **Verify**.
6. All required chats are checked **concurrently**:
   - actual member = accepted
   - recent captured pending join request = accepted
   - neither = missing
7. When verification succeeds, the original inline Join/Verify buttons are removed automatically.
8. First video batch unlocks.
9. Next batches unlock through verified referrals.

## Fast parallel verification

Verification uses `asyncio.gather()` so required chats are checked in parallel instead of sequentially. This matters when many force-join chats are configured.

## Pending request recognition

The bot listens for Telegram `chat_join_request` updates. A recent request is stored in MongoDB with:

- `chat_id`
- `user_id`
- `requested_at`
- invite-link metadata

Default validity window:

```env
PENDING_REQUEST_TTL_HOURS=72
```

If the user sends a new request later, the timestamp is refreshed.

## Required group setup

Open:

```text
/admin
→ ➕ Add Required Group
```

Send only the numeric chat ID.

The bot will:
- read the chat title
- generate its own invite link with `creates_join_request=True`
- save that approval link in MongoDB
- use it in the force-join UI

The bot must be admin and have permission to create invite links.

If you later want to override one chat with your own link:

```text
/setcustomlink
```

Then send the chat ID and custom `t.me` link.

## Unlimited video upload until DONE

Open:

```text
/admin
→ 📤 Upload Videos
```

Send/forward as many videos as you want.

Behavior:
- every video is copied to the private storage channel
- every 10 videos = one batch automatically published
- send `DONE` when finished
- if 1–9 videos remain, the bot publishes one final partial batch
- upload mode then turns OFF

So 103 videos become:
- batches 1–10 = 10 videos each
- batch 11 = 3 videos

## Protected delivery + 12 hour deletion

User-delivered videos use:

```python
protect_content=True
```

The sent video message IDs and deletion timestamps are stored in MongoDB. Default:

```env
DELETE_AFTER_HOURS=12
```

The cleanup worker continues correctly after bot/server restart.

## Storage channel

Create one private Telegram channel and add the bot as admin.

```env
STORAGE_CHANNEL_ID=-100...
```

All video files stay there. MongoDB stores the source `message_id` mappings.

A replacement bot can use the same storage channel/message IDs after being added to the channel.

## Leave detection fix

The bot now listens to `chat_member` updates for configured required chats.

- member joins/gets approved -> stale pending request is removed
- member leaves/is removed -> verification is revoked immediately
- old pending requests from before the leave no longer satisfy verification
- the user must submit a fresh join request / rejoin and verify again

Keep the bot as admin in required chats so Telegram can deliver the relevant membership updates reliably.


## Strict membership verification fix

This build treats `getChatMember` as the authoritative current-state check.

- current member/admin/owner -> verified
- current non-member/left/kicked -> NOT verified
- a pending request is only accepted if it is fresh
- if the user left before, an old pending request is invalid
- only a new join request created after the leave can satisfy pending status

Troubleshooting:

```text
/checkme
```

shows per-required-chat state as `member`, `pending`, or `missing`.


## 24-hour approval request verification

No Telegram user session is required.

- public/custom-link chats: actual membership only
- approval-link chats: actual membership first
- if not yet a member, a captured `chat_join_request` remains valid for 24 hours
- MongoDB TTL deletes the temporary pending record automatically
- actual join or leave clears that user's pending marker

For Telegram to send `chat_join_request`, the bot must be an administrator in the
target chat with the `can_invite_users` right.

Debug with:

```text
/checkme
```

It shows:
- current state (`member`, `pending`, `missing`)
- configured link mode
- whether the temporary pending record exists


## Smarter `/start`

`/start` no longer blindly shows every force-join link.

On every `/start` the bot first verifies all required chats in parallel:

- member -> hidden
- valid 24h pending approval request -> hidden
- missing -> only that chat's Join button is shown
- nothing missing -> Video Vault opens directly

So already-completed groups are never shown again unnecessarily.

## Remove a required group/channel

Open `/admin` → `🗑 Remove Required Channel` → select a chat → `✅ Yes, Remove`. The bot removes only the selected force-join requirement plus its temporary pending and membership-event data. The Telegram chat, uploads, user unlocks, and remaining required chats are untouched. The confirmation screen has Back and Cancel buttons.

## Clean shutdown fix

The video deletion worker now starts via `asyncio.create_task` in `post_init` and is cancelled/awaited by `post_stop` on Ctrl+C. Pending deletion records remain in MongoDB and are picked up after restart.


## Storage forwarding restriction fix

New videos copied to the storage channel use `protect_content=False`. Copies delivered to users still use `protect_content=True`, and the 12-hour deletion worker is unchanged.

**Important:** This only affects NEW storage copies. Telegram does not let this flag retroactively unprotect previously copied messages. If your existing storage messages are protected, re-upload from an unrestricted original source and rebuild their message-ID mappings using the admin upload workflow. If the storage channel itself has **Restrict Saving Content** enabled, disable that in the channel settings too; the bot cannot override the channel-level setting.


## Storage copy retry and error diagnostics

- Copying media to storage uses Telegram `copy_message` (no server-side download/upload).
- Latest build uses one storage copy worker with a minimum 2-second gap, and a shared Telegram cooldown.
- Completed source/storage message mappings are stored in MongoDB before DONE.
- DONE drains outstanding copies and reports failures by source message ID and safe error type.
- Retry Failed retries only unsuccessful video IDs, without reuploading the first successful videos.
- Publish Successful explicitly skips failed videos and publishes successes in their original source-message order.
- For very large batches, keep sequential copying. Increase `UPLOAD_COPY_GAP_SECONDS` above 2 if Telegram still throttles.
- On a network timeout, Telegram may have copied the video even if the response was lost; retries can leave extra copies in the storage channel.
- When upgrading during an unfinished upload from an older version, complete the old version's DONE first so no draft is overwritten.


## Storage pacing / shared FloodWait fix (latest)

- **One** storage-copy worker, even if the old server `.env` says `UPLOAD_CONCURRENCY=3`.
- At least **2 seconds after each copy attempt** before the next starts; configurable upward with `UPLOAD_DELAY_SECONDS=2` (also accepts legacy `UPLOAD_COPY_GAP_SECONDS=2`).
- On Telegram `RetryAfter`, the **entire storage copy queue** waits the time Telegram requests, plus a 1-second cushion.
- Uploads are still `copy_message` to the storage channel (`protect_content=False`); no download or re-upload is needed. Users' delivered videos are still protected and deleted after 12 hours.
- `DONE` waits for queued copies; source message order is preserved when making 10-video batches. `Retry Failed` continues to retry failed source message IDs.
- The required Telegram wait cannot be overridden; 2 seconds is a pacing starting point, not a guarantee that Telegram will never apply limits.

**Upgrade:** If an upload is active, finish it using `DONE` on the old bot, then stop it and install this zip. Existing `.env` and MongoDB are reused.

## Live storage upload progress (new)

During **📤 Upload Videos** a separate **📊 LIVE STORAGE UPLOAD** bot-owned message is created and edited approximately every 3 seconds while uploading. It shows: received, copied to storage, failed, pending, percent of currently received videos processed, current source video and countdown when Telegram applies `RetryAfter`. Copy successes/failures are read from MongoDB, so it does not misreport a video as stored simply because Telegram received it. No extra message is sent per video.

Use the **📊 Upload Status** reply-keyboard button or `/uploadstatus` for a fresh one-time snapshot. `DONE` keeps the live message updating while it drains the queue. If you need to retry failures, the live message continues; on completion or cancellation it is closed. An old draft's persisted counts remain available after restart, but a running Telegram transfer cannot survive a process restart.

Optional `.env`:

```env
UPLOAD_CONCURRENCY=1
UPLOAD_DELAY_SECONDS=2
UPLOAD_PROGRESS_REFRESH_SECONDS=3
```

Telegram may still apply FloodWait; the progress display is intentionally throttled and will not override Telegram's required wait.
